# 경쟁 제품 리서치 지침

## 적용 경계

claw는 외부 공개 정보 수집, 비교표 작성, 요약, 출처 검증, 메시지화까지 처리한다.

다음이 포함되면 구현 전에 advisor에게 먼저 위임한다.

- repo 파일을 읽거나 수정해야 하는 경쟁 분석
- 수집 결과를 바탕으로 스키마·데이터 구조·아키텍처를 정해야 하는 경우
- "어떤 방향이 좋을까", "처음부터 좋은 구조로"처럼 의사결정 경계가 불명확한 경우
- 리서치 결과를 yeojin-context-hub 문서, 티켓, 프로젝트 구조에 반영해야 하는 경우

고지 문구는 한 줄로 끝낸다.

> "→ 리서치 결과를 레포 구조/설계 판단에 반영해야 해 advisor에게 위임했습니다."

## 사실 신뢰도 등급 표시

리서치 결과의 모든 주요 항목은 세 등급 중 하나로 표시한다.

| 등급 | 표기 | 사용 조건 |
|------|------|-----------|
| 확인됨 | `확인됨 — [출처]` | 공식 문서, README, changelog, 코드, 회사 공지에서 직접 확인 |
| 추론 | `추론 — 근거: [이유]` | 코드 구조, 제품 흐름, 복수 출처의 정황에서 합리적으로 유추 |
| 미검증 | `~X (미검증, 출처 불분명)` | 수치·통계·기능 등 출처를 확인하지 못한 경우 |

수치(토큰 수, 응답 시간, 사용자 수, 가격, 매출 등)는 반드시 출처를 병기하거나 "(미검증 추정)"으로 표기한다.

## 체크리스트

제품마다 아래 4항목을 같은 순서로 확인한다. 확인하지 못한 항목은 "미확인"으로 쓴다.

1. **아키텍처**: LLM API 직접 호출, CLI wrapper, agent framework, 혼합 구조
2. **토큰·비용·성능**: 실제 측정치와 추정치를 구분하고 측정 조건 명시
3. **기능 목록**: 공식 changelog/README 기준, 버전 또는 확인 날짜 명시
4. **한계점**: 공식 issue tracker, 커뮤니티 피드백, 직접 테스트 근거 구분

## 웹 조회 원칙

codex 내장 `web_search = "cached"`를 먼저 활용한다. 최신성이 핵심이면 캐시 무효화를 명시한다.

외부 fetch가 필요하면 PowerShell 기준으로 다음 순서를 따른다.

```powershell
curl.exe -A "Mozilla/5.0" <url>
```

HTML 접근이 막히면 RSS 또는 feed URL을 시도한다.

- `https://rss.<domain>/<id>.xml`
- `<url>/feed`

## 병렬 비교

경쟁 제품 2개 이상을 비교할 때는 codex `multi_agent` 또는 가능한 병렬 분해를 사용해 제품별 4항목을 따로 수집한 뒤, 최종 답변에서 같은 항목끼리 표로 정렬한다.

Node REPL MCP로 changelog JSON, release notes, package metadata를 파싱해도 된다.

## Discord 출력 계약

최종 답변은 Discord에 그대로 전달될 수 있게 간결하게 작성한다.

- 2000자를 넘길 가능성이 있으면 핵심 요약과 표만 먼저 제공한다.
- URL이나 파일 산출물이 있으면 마지막 줄에 artifact JSON을 붙인다.
- 파일 산출물: `__CLAW_ARTIFACT__ {"kind":"file","path":"C:\\...","caption":"설명"}`
- URL 산출물: `__CLAW_ARTIFACT__ {"kind":"url","url":"https://...","caption":"설명"}`
- 여러 문의·메일·고객 건을 비교 보고할 때는 채널, 수신 시각, 연락처, 원문을 생략하지 않는다.

## 검증과 반복 패턴

리서치 완료 전 최소 dry-run 검증을 수행한다.

- 출처 URL 재접속 가능 여부 확인
- 핵심 수치가 출처 본문에 실제 존재하는지 확인
- 표의 "확인됨/추론/미검증" 등급 누락 여부 확인

반복 가능한 수집·비교 스크립트나 워크플로우를 새로 만들었다면, 완료 전에 관련 skill에 패턴 추가를 먼저 제안한다.

## 3-cycle 점검 루프

1. **Cycle 1 — 경계 확인**: claw 단독 처리인지, advisor 설계 판단이 필요한지 먼저 판정한다.
2. **Cycle 2 — 출처 검증**: 공식·1차 출처 우선으로 사실 등급을 붙이고 미검증 수치를 분리한다.
3. **Cycle 3 — 전달 검증**: Discord 길이, artifact JSON, 다음 행동, dry-run 결과가 최종 답변에 포함됐는지 확인한다.
