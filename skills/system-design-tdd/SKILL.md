# 시스템 설계 응답 원칙 (Kent Beck 스타일)

## advisor 우선 라우팅

시스템 설계, 스키마, 아키텍처, 데이터 구조, 방향 불확실성이 감지되면 구현 착수 전에 advisor에게 먼저 위임한다.

즉시 위임 대상:

- "스키마 만들자", "구조 어떻게 잡을지", "필드가 뭐가 필요할지"
- "아키텍처 설계", "처음부터 좋은 구조", "전체 설계"
- "뭐가 좋을까", "어떤 방식이 나을지", "방향을 잡고 싶어"
- yeojin-context-hub repo 파일 생성·수정·커밋이 필요한 설계

고지 문구는 한 줄로 끝낸다.

> "→ 구조 설계 판단이 필요해 advisor에게 위임했습니다."

예외:

- 사용자가 이미 방향을 확정하고 "그 구조대로 만들어줘"라고 한 경우
- 단순 오타, 이름 변경, 이미 합의된 문서 업데이트
- 사용자가 advisor 위임을 명시적으로 거부한 경우

## 설계 원칙

1. **Make it work → right → fast** 순서를 명시하고 바꾸지 않는다.
2. 각 slice는 독립 배포 가능하고 완료 기준이 명확해야 한다.
3. 투기적 설계는 금지한다. 데이터가 필요성을 증명하면 추가한다.
4. slice가 5개를 초과하면 phase로 묶는다.

## 응답 구조

1. **원칙**: 3줄 이내
2. **최종 데이터 구조**: 핵심 스키마만
3. **Slice 1~N**: 목표 한 줄, 완료 기준, 핵심 구현 포인트
4. **검증**: 실행 또는 dry-run 명령
5. **다음 단계**: Slice 1부터 시작

## Windows / git / push 규율

repo 작업으로 이어지는 설계라면 PowerShell 7.6.x 기준으로 명령을 쓴다.

- 환경변수: `$env:VAR_NAME`
- 홈: `$env:USERPROFILE`
- 줄 연속: 백틱
- 리다이렉트: `2>$null`
- 체이닝: `&&`, `||`
- bash 문법 금지

작업 완료 후 commit/push가 요구된 경우:

```powershell
gh auth setup-git
git remote get-url origin
```

remote가 SSH(`git@github.com:...`)이면 HTTPS로 전환 후 push한다. 실패 시 강행 옵션(`-f`, `--no-verify`, `--no-gpg-sign`)은 사용하지 않고 보고한다.

## Discord 출력 계약

최종 보고는 다음 3단 구조를 지킨다.

1. **구현 내용**
2. **검증 결과**
3. **다음 단계**

파일이나 URL 산출물이 있으면 마지막 줄에 artifact JSON을 붙인다.

## 반복 워크플로우 패턴 제안

설계 과정에서 반복 가능한 스크립트, task spec, migration, 검증 루틴을 새로 만들었다면 구현 전에 "관련 skill에 패턴을 추가하겠다"고 제안한다.

## 3-cycle 점검 루프

1. **Cycle 1 — 의도/경계**: 사용자의 의도와 advisor 위임 필요성을 판정한다.
2. **Cycle 2 — 슬라이스 검증**: 각 slice가 독립 배포 가능하고 완료 기준이 테스트 가능한지 확인한다.
3. **Cycle 3 — 실행 검증**: PowerShell 명령, git/push 규율, 최종 3단 보고 형식을 확인한다.
